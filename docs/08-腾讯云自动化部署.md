# 08 · 腾讯云自动化部署

> 前面 7 章解决了「**本地能跑**」。
> 这一章解决「**放到公网上、别人能访问、挂了能自己恢复、密码不泄露**」。
>
> 一句话概括这章要做的事：
> **把「登录服务器 → 敲十几条命令」变成「执行一条命令」。**

---

## 0. 先搞清楚「自动化」到底有几种程度

很多人一上来就说「我要 CI/CD」，其实自动化是分层的。先看清自己在哪一层，别一步跨太大。

| 级别 | 做法 | 一次发布要多久 | 适合谁 |
| --- | --- | --- | --- |
| L0 纯手动 | SSH 上去 `git pull`、`docker compose up -d --build` | 5~15 分钟，还容易敲错 | 学习、临时演示 |
| L1 脚本化 | 本地执行一条命令，脚本负责上传 + 部署 + 健康检查 | 1~3 分钟 | **个人项目 / 小团队，性价比最高** |
| L2 流水线 | push 到 main，CI 自动构建、测试、部署、失败通知 | 完全不用管 | 多人协作、需要审计 |
| L3 容器平台 | 镜像推仓库，Kubernetes 滚动更新、自动扩缩容 | 无需关心机器 | 有一定规模 |

**本章给你 L1 + L2 两套，都能直接跑。**

```
你现在的状态                        本章结束后的状态
┌──────────────┐                  ┌──────────────────────────────┐
│ 本地能跑      │  ────────────►   │ https://你的域名             │
│ localhost    │                  │ 挂了自动回滚                  │
│ 密码写死在代码│                  │ 密码全在 .env（600 权限）     │
└──────────────┘                  │ 每天自动备份                  │
                                  └──────────────────────────────┘
```

L1 的完整链路长这样，先有个印象：

```
你的 Windows                   腾讯云 CVM
┌─────────────┐   scp 打包上传  ┌──────────────────────────────┐
│ publish.ps1 │ ──────────────► │ tar 解包                     │
└─────────────┘                 │   ↓                          │
                                │ sed 去掉 Windows 的 \r       │
                                │   ↓                          │
                                │ deploy.sh                    │
                                │   ├─ 校验 .env               │
                                │   ├─ 生成 runtime 配置       │
                                │   ├─ docker compose build    │
                                │   ├─ up -d                   │
                                │   ├─ 健康检查（失败自动回滚）│
                                │   └─ 清理旧镜像              │
                                └──────────────────────────────┘
```

## 1. 买机器：腾讯云怎么选

### 1.1 两个产品，别买错

腾讯云有两种「服务器」，新手最容易选错：

| | 轻量应用服务器（Lighthouse） | 云服务器 CVM |
| --- | --- | --- |
| 定位 | 套餐式，开箱即用 | 弹性、可自由组合 |
| 价格 | 便宜（常有新用户活动） | 稍贵，按配置计费 |
| 带宽 | 套餐内含固定带宽（如 4Mbps） | 单独购买带宽/流量 |
| 防火墙 | 在控制台叫「防火墙」，配置更简单 | 叫「安全组」，规则更细 |
| 能不能跑本项目 | **能，推荐** | 能 |

> **建议：第一次部署选「轻量应用服务器」**，界面简单、价格透明、自带防火墙面板。
> 等你要做多机集群、挂载云硬盘、接负载均衡 CLB 时，再换 CVM。

### 1.2 配置建议

本项目在一台机器上跑 **8 个常驻容器**：Nginx 入口 + 前端 + 3 个后端 + Redis + 2 个 MySQL（外加一个跑完就退出的 `replica-init`）。

| 配置 | 能不能跑 | 说明 |
| --- | --- | --- |
| 1 核 2G | 勉强 | 构建前端时极可能 OOM，靠 swap 硬撑，**不推荐** |
| **2 核 4G** | ✅ 推荐 | 构建顺畅，日常内存占用约 2.2G |
| 2 核 2G | 可以 | 必须加 swap（脚本会加），构建时慢一些 |
| 4 核 8G | 宽裕 | 想在上面再跑点别的东西就选这个 |

磁盘：**至少 40G**。Docker 镜像 + MySQL 数据 + 备份，20G 很快满。

> ⚠️ **磁盘满是最常见的线上故障**。本项目的 compose 已配好日志轮转（每个容器最多 10MB × 3 个），但你自己 `docker build` 出来的旧镜像没人删，`deploy.sh` 每次会 `image prune` 一次兜底。

### 1.3 系统镜像

选 **Ubuntu 22.04 LTS** 或 **24.04 LTS**。

为什么不用 CentOS？CentOS 7 已停止维护，CentOS Stream 又偏滚动。Ubuntu 的软件源新、Docker 装起来最省事，本章脚本也是按 Ubuntu 写的（用 `apt`）。

### 1.4 地域，以及一个必须提前知道的事

- 用户在国内 → 选**上海 / 广州 / 北京**，延迟低。
- 用户主要在海外 → 选**香港**或新加坡。

> 📌 **备案提醒（只针对中国大陆地域）**
> 在中国大陆地域的服务器上，用域名通过 80/443 对外提供网站服务，需要先完成 ICP 备案；未备案的域名访问会被拦截。
> 香港及海外地域没有这个要求。
> **如果只是想先跑通技术流程、暂时没有备案域名**，有两条路：
> 1. 直接用 `https://公网IP` 访问（证书会报域名不匹配，浏览器可手动信任）；
> 2. 买香港地域的机器。
>
> 备案本身是行政流程，跟代码无关，这里只做提醒。

## 2. 开门：安全组、SSH、域名

### 2.1 安全组只开三个口

把服务器想象成一栋楼，安全组就是门禁：**没登记的端口，外面根本敲不到门**。

| 端口 | 协议 | 来源 | 用途 |
| --- | --- | --- | --- |
| 22 | TCP | **只填你自己的公网 IP**（不要 0.0.0.0/0） | SSH 登录 |
| 80 | TCP | 0.0.0.0/0 | HTTP（跳转 + 证书校验） |
| 443 | TCP | 0.0.0.0/0 | HTTPS |

**其它端口一个都别开。** 特别注意：

- `3306`（MySQL）、`6379`（Redis）**绝对不要对公网开放**。公网上的 Redis 未授权访问是最常见的入侵入口之一。
- `8000`（后端）、`8080`（旧版入口）也不要开。

本项目生产编排里根本没写这些端口映射 —— 不是忘了，是故意的：**容器之间走 Docker 内网，外面的世界只能看到 443**。

> 💡 想临时从本机连数据库调试？用 SSH 隧道，别开端口：
> ```powershell
> ssh -i 你的密钥 -L 3307:127.0.0.1:3306 deploy@服务器IP
> # 然后本地连 127.0.0.1:3307
> ```
> 但生产编排没映射 3306 到宿主机，隧道也连不到 —— 需要临时 `docker compose exec` 进去看。这是刻意的取舍。

### 2.2 用密钥登录，别用密码

腾讯云创建实例时会让你选密钥对或设置密码。**选密钥对**。

下载的 `.pem` 文件就是你的钥匙：

```powershell
# Windows：把权限收紧，否则 ssh 会拒绝使用
icacls.exe "$HOME\.ssh\tc.pem" /inheritance:r /grant:r "$($env:USERNAME):(R)"

ssh -i "$HOME\.ssh\tc.pem" ubuntu@1.2.3.4
```

腾讯云 Ubuntu 镜像默认用户是 `ubuntu`（不是 root），可以 `sudo`。

> 🔒 想彻底关掉密码登录（防爆破）？确认密钥能登录后再做：
> ```bash
> sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
> sudo systemctl restart ssh
> ```
> **顺序别搞反**，否则你会把自己锁在门外。改之前先开一个窗口保持登录状态。

### 2.3 域名解析

在腾讯云「DNSPod」里加一条 A 记录：

| 主机记录 | 记录类型 | 记录值 |
| --- | --- | --- |
| `app` | A | 服务器公网 IP |

过几分钟，`ping app.你的域名.com` 能通就说明解析生效了。

验证一下（在服务器上）：

```bash
dig +short app.example.com
# 应该输出你的公网 IP
```

> 📌 注意：`DOMAIN` 里**不要带 `https://`、不要带路径**，只要 `app.example.com`。

## 3. 初始化服务器（一条命令）

### 3.1 先把代码弄上去

三种方式，任选：

**方式 A：本地脚本上传（Windows 推荐）**

```powershell
cd i:\work-body-dir\fullstack-cluster-tutorial
.\scripts\cloud\publish.ps1 -ServerHost 1.2.3.4 -User ubuntu -KeyPath "$HOME\.ssh\tc.pem" -SkipDeploy
```

`-SkipDeploy` 表示只上传不部署 —— 现在服务器还没准备好，先传代码。

**方式 B：git clone**

```bash
sudo mkdir -p /opt/fullstack-cluster-tutorial
sudo chown -R $USER:$USER /opt/fullstack-cluster-tutorial
git clone 你的仓库地址 /opt/fullstack-cluster-tutorial
```

**方式 C：SFTP 工具**（WinSCP / FileZilla）拖上去。

### 3.2 跑初始化脚本

```bash
cd /opt/fullstack-cluster-tutorial
sudo bash scripts/cloud/init-server.sh
```

> ⚠️ 如果你的 `.sh` 文件是在 Windows 上编辑过再传上来的，可能带 CRLF 换行，bash 会报 `$'\r': command not found`。
> 先执行一次：
> ```bash
> sudo sed -i 's/\r$//' scripts/cloud/*.sh
> ```

它大概跑 2~5 分钟，做完会打印下一步提示。

### 3.3 它到底改了什么

| 步骤 | 做了什么 | 为什么必须做 |
| --- | --- | --- |
| 1 | 装 `curl git jq unzip rsync gettext-base ufw fail2ban openssl` | 后面脚本都要用，`gettext-base` 提供 `envsubst` |
| 2 | 时区设为 `Asia/Shanghai` | 否则日志时间是 UTC，排查问题时对不上 |
| 3 | 装 Docker + compose 插件 | 官方脚本，国内机器配腾讯云内网镜像加速 |
| 4 | 创建 `deploy` 用户并加入 docker 组 | 日常部署不用 root，降低误操作风险 |
| 5 | 加 2G swap | **1~2G 内存的机器不加 swap，构建前端必 OOM** |
| 6 | 防火墙只放行 22/80/443 | 和云控制台的安全组是两层防护，都要配 |
| 7 | fail2ban | SSH 连续失败 5 次封 10 分钟，挡掉大部分爆破 |
| 8 | `vm.overcommit_memory=1` | Redis 官方建议，避免 fork 时 OOM |

两个容易被忽略的细节，值得单独说：

**① 为什么脚本里 `ufw allow 22` 写在 `ufw enable` 前面？**

因为 `ufw --force enable` 会立刻按规则拦截所有未放行的流量。如果先 enable 再放行 22，你的 SSH 连接会当场断掉，而且再也连不上（只能去控制台 VNC 救）。

**② 为什么一定要 swap？**

前端构建（Vite + Rollup）是内存大户，2G 内存的机器在 `npm run build` 时峰值能到 1.5G 以上，直接 OOM 被内核杀掉，日志里只有一句 `Killed`，非常难查。加了 swap 之后最多慢一点，不会失败。

### 3.4 顺便验证一下

```bash
docker --version
docker compose version
ufw status
free -h          # 看 swap 有没有生效
```

## 4. 把密码从代码里赶出去

这是**上公网前最关键的一步**，比装什么软件都重要。

### 4.1 教学版 vs 生产版

你在本地跑的教学版，密码是写死在 compose 里的：

```yaml
MYSQL_ROOT_PASSWORD: rootpass
MYSQL_PASSWORD: demo123
REDIS_URL: redis://:redispass@redis:6379/0
```

这套东西如果原样搬上公网，等于**把家门钥匙插在锁上**。生产版全部改成从 `.env` 读取：

| 配置项 | 教学版 | 生产版 |
| --- | --- | --- |
| MySQL root 密码 | `rootpass` | `.env` 中随机 24 位 |
| MySQL 业务密码 | `demo123` | `.env` 中随机 24 位 |
| MySQL 复制密码 | `replpass` | `.env` 中随机 24 位 |
| Redis 密码 | `redispass` | `.env` 中随机 24 位 |
| 演示账号 alice/bob | 自动创建 | **`SEED_DEMO_USERS=false` 不创建** |
| 调试接口 `/api/auth/session` | 开放 | `ENABLE_DEBUG_ENDPOINTS=false` 返回 404 |
| 数据库端口 | 映射到宿主机 | **不映射** |
| Cookie Secure | false（HTTP） | **true（只走 HTTPS）** |

### 4.2 创建 .env

```bash
cd /opt/fullstack-cluster-tutorial/deploy/cloud
cp .env.production.example .env
chmod 600 .env            # 只有属主能读，别人 cat 都看不到
```

`.gitignore` 已经忽略了这个文件，它不会被提交、也不会被 `publish.ps1` 覆盖。

### 4.3 生成 5 个密码

一条命令生成一个，复制到 `.env` 对应位置：

```bash
openssl rand -base64 24 | tr -dc 'A-Za-z0-9' | head -c 24; echo
```

需要填的 5 个：

| 变量 | 干什么用的 | 注意 |
| --- | --- | --- |
| `MYSQL_ROOT_PASSWORD` | MySQL 超级管理员 | 只在运维时用，应用不用它 |
| `MYSQL_PASSWORD` | 应用连数据库的账号 | 应用日常用的就是这个 |
| `MYSQL_REPL_PASSWORD` | 主从复制专用账号 | 只有从库用它拉 binlog |
| `REDIS_PASSWORD` | Redis 密码 | 会话数据全靠它保护 |
| `ADMIN_INITIAL_PASSWORD` | 首次启动创建 `admin` 账号 | 登录后建议改掉 |

再加一个 `DOMAIN`，比如 `app.example.com`。

### 4.4 演示账号必须关掉

```dotenv
SEED_DEMO_USERS=false
ADMIN_INITIAL_PASSWORD=你生成的强密码
```

为什么这么重要？`alice / 123456` 这种账号一旦暴露在公网，扫描器几分钟内就能登进来。项目里没有注册接口，所以关掉演示账号后，靠 `ADMIN_INITIAL_PASSWORD` 创建唯一的管理员。

> 这个开关在 `backend/app/database.py` 里，只在**首次初始化数据库**时生效。如果数据库已经初始化过，改这个变量不会删除已有账号 —— 需要手动执行：
> ```sql
> DELETE FROM users WHERE username IN ('alice','bob');
> ```

### 4.5 密码里别用特殊字符

连接串是这样的：

```
mysql+pymysql://appuser:密码@mysql-master:3306/fullstack_demo
```

如果密码里有 `@`、`:`、`/`、`?`、`#`，连接串会被解析错，报一些看不懂的错（比如找不到主机、认证失败）。

**所以生成的密码只用大小写字母 + 数字**，上面的 `tr -dc 'A-Za-z0-9'` 就是在做这件事。

同理，`.env` 是用 `source` 加载的，值里不要有空格和引号。

## 5. HTTPS：三条路，按需选

生产版 Nginx 强制 HTTPS，所以必须先有证书。三种方式：

### 方式 A：腾讯云免费 SSL 证书（最省心，推荐新手）

1. 控制台 → 「SSL 证书」→ 申请免费证书（DV 类型）
2. 填域名，选 DNS 验证，按提示在 DNSPod 加一条 TXT 记录
3. 一般几分钟内签发
4. 下载 → 选 **Nginx 格式**，得到一个 `.crt` 和 `.key`
5. 上传到服务器并改名：

```bash
cd /opt/fullstack-cluster-tutorial/deploy/cloud/certs
# 本地 scp 上传后：
mv 你的域名_bundle.crt fullchain.pem
mv 你的域名.key privkey.pem
chmod 600 privkey.pem
```

> 📌 免费证书有效期通常为 90 天，到期前记得续。可以在日历上设个提醒，或者直接用方式 B 自动续。

### 方式 B：acme.sh 自动申请 + 自动续期（推荐长期用）

```bash
# 安装
curl https://get.acme.sh | sh -s email=你的邮箱

# 用 DNS 方式验证（推荐，不需要 80 端口配合）
export DP_Id="你的DNSPod API ID"
export DP_Key="你的DNSPod API Key"
~/.acme.sh/acme.sh --issue --dns dns_dp -d app.example.com

# 安装证书到项目目录，并设置续期后自动重启 nginx
~/.acme.sh/acme.sh --install-cert -d app.example.com \
  --key-file       /opt/fullstack-cluster-tutorial/deploy/cloud/certs/privkey.pem \
  --fullchain-file /opt/fullstack-cluster-tutorial/deploy/cloud/certs/fullchain.pem \
  --reloadcmd      "cd /opt/fullstack-cluster-tutorial/deploy/cloud && docker compose --env-file .env -f docker-compose.prod.yml restart lb"
```

acme.sh 会自己加一条 cron，到期前自动续，续完自动 restart nginx。**一次配好，长期不用管**。

### 方式 C：自签证书（只用于先跑通）

什么都不用做 —— `deploy.sh` 发现 `certs/` 里没有证书时，会自动生成一张 30 天的自签证书，让服务先起来。

浏览器会显示「不安全」，但**功能完全正常**，可以用来验证整个流程。等正式证书到位，替换两个文件后 restart 即可。

### 换证书之后

```bash
cd /opt/fullstack-cluster-tutorial/deploy/cloud
docker compose --env-file .env -f docker-compose.prod.yml restart lb
```

> ⚠️ 模板里带了 HSTS 响应头（`Strict-Transport-Security`）。一旦浏览器收到过这个头，它会在有效期内**强制**用 HTTPS 访问你的域名，即使你后来把证书撤了也改不回来（除非换域名或清浏览器缓存）。
> 所以：**先用自签证书跑通、确认没问题，再换正式证书**。如果你在测试阶段反复折腾证书，可以先把这一行注释掉。

## 6. 一键部署

### 6.1 执行

```bash
cd /opt/fullstack-cluster-tutorial
bash scripts/cloud/deploy.sh
```

第一次大约 **3~8 分钟**（构建镜像占大头），之后每次 1~3 分钟。

### 6.2 deploy.sh 的七个步骤

```
① 校验 .env ──────► 有 CHANGE_ME 就停下，权限不是 600 就自动改
② 生成 runtime ───► envsubst 把密码写进 redis.conf / 01-init.sql
③ 检查证书 ───────► 没有就生成自签证书
④ 记录上一版 ─────► 把当前镜像打成 :rollback
⑤ 构建 + 启动 ────► docker compose build / up -d
⑥ 健康检查 ───────► 3 个副本都 healthy 且 Nginx 能响应急速
⑦ 失败回滚 ───────► 用 :rollback 重新起，然后退出并打印日志命令
```

几个设计上的用心之处：

**为什么第 ① 步要检查 `CHANGE_ME`？**
因为新手最常见的错误就是 `cp` 完忘了改，直接部署。与其等到数据库连不上再排查，不如提前拦住并明确告诉你「哪一行没改」。

**为什么第 ② 步要生成文件，而不是直接在 compose 里传环境变量？**
- `redis.conf` 不支持环境变量，必须生成实体文件。
- 更重要的：`docker inspect` 会把容器的命令行完整打印出来。如果你用 `--requirepass 明文密码`，任何能执行 docker 命令的人都能看到密码。写进权限 600 的文件里，安全得多。

**为什么第 ③ 步要自动生成自签证书？**
否则 Nginx 会因为「找不到证书文件」直接启动失败，报 `cannot load certificate`，新手很难理解这是证书问题。先生成一张临时的，让整条链路先通。

**为什么第 ⑥ 步要检查 3 个副本，而不是只看容器在不在？**
容器「Running」不等于「能干活」。可能进程起来了但连不上 Redis、或者表还没建好。Docker 的 `healthcheck` 是真的发一个 HTTP 请求到 `/api/system/health`，通过才算 healthy。

**为什么第 ⑦ 步要回滚？**
部署失败时最怕的不是失败，而是**留下一个半死不活的状态**。自动切回上一版镜像，至少保证线上是可用的，然后你慢慢排查。

### 6.3 手动回滚

```bash
bash scripts/cloud/rollback.sh              # 回上一版
bash scripts/cloud/rollback.sh 20261103-101500   # 回指定版本
```

回滚只是「用旧镜像重新起容器」，**不动数据库**。所以如果这次发布改了表结构，回滚代码后可能对不上 —— 这也是为什么生产环境改表要单独走流程（先加字段、再发代码、最后删旧字段）。

### 6.4 部署完立刻看一眼

```bash
cd /opt/fullstack-cluster-tutorial/deploy/cloud
docker compose --env-file .env -f docker-compose.prod.yml ps
```

正常应该看到 8 个容器，其中 `backend-1/2/3`、`mysql-*`、`redis`、`lb` 是 `healthy`，`replica-init` 是 `exited (0)`（一次性任务，正常退出）。

## 7. 三种触发方式

### 方式 A：本地 PowerShell（最常用，L1）

```powershell
cd i:\work-body-dir\fullstack-cluster-tutorial
.\scripts\cloud\publish.ps1 -ServerHost 1.2.3.4 -User ubuntu -KeyPath "$HOME\.ssh\tc.pem"
```

它做三件事：打包（自动排除 `node_modules`、`.git`、`.env`）→ scp 上传 → ssh 远程执行 `deploy.sh`。

**为什么排除 `.env`？** 服务器上的 `.env` 是你精心配置的，不能被本地文件覆盖。这是很多人踩过的坑：本地一套配置，一发布把线上密码冲掉了。

### 方式 B：GitHub Actions（L2）

仓库里已经放好 `.github/workflows/deploy-cloud.yml`，推送到 `main` 就自动部署。

配置 4 个 Secrets（Settings → Secrets → Actions）：

| Secret | 内容 |
| --- | --- |
| `DEPLOY_SSH_KEY` | 私钥**全文**，包含 `-----BEGIN...` 和 `-----END...` |
| `SERVER_HOST` | 服务器公网 IP |
| `DEPLOY_USER` | `ubuntu` 或 `deploy` |
| `APP_DIR` | `/opt/fullstack-cluster-tutorial` |

对应的公钥要加到服务器的 `~/.ssh/authorized_keys`。

> ⚠️ GitHub Actions 的机器人在海外，访问腾讯云服务器偶尔会慢。如果 push 之后迟迟没动静，去 Actions 页面看日志，通常是 SSH 连接超时。

### 方式 C：腾讯云 CODING DevOps（L2，国内更稳）

如果你的代码在国内平台，用腾讯云自家的 CODING 流水线，步骤完全一样：

1. 创建项目 → 代码仓库 → 关联你的仓库
2. 持续集成 → 新建构建计划 → 选「自定义构建过程」
3. 添加「执行 Shell 脚本」步骤，内容就是 `deploy.sh` 那几行
4. 在「凭据管理」里存 SSH 私钥，构建时注入

好处是**执行机在国内**，拉代码、传文件都快，而且和 CVM 在同一内网时还能走内网 IP。

### 三种方式怎么选

| | 本地脚本 | GitHub Actions | CODING |
| --- | --- | --- | --- |
| 上手成本 | 最低 | 中 | 中 |
| 需要公网 Git 仓库 | 否 | 是 | 是 |
| 国内速度 | 取决于你家宽带 | 一般 | 快 |
| 适合 | 个人项目、快速迭代 | 开源/海外协作 | 企业、国内团队 |

## 8. 上线验收清单

部署成功不等于做对了。逐条过一遍：

### 8.1 基础访问

```bash
curl -I https://app.example.com                 # 200，且能看到 Strict-Transport-Security
curl -s https://app.example.com/api/system/health
# {"status":"ok","instance":"backend-2"}
```

多刷几次，`instance` 应该在 `backend-1/2/3` 之间轮转 —— **这就是负载均衡生效的证据**。

### 8.2 HTTP 自动跳 HTTPS

```bash
curl -I http://app.example.com
# HTTP/1.1 301 → Location: https://app.example.com/
```

### 8.3 Cookie 属性对不对

浏览器登录后按 F12 → Application → Cookies，检查 `session_id`：

| 属性 | 应该是 | 说明 |
| --- | --- | --- |
| `HttpOnly` | ✅ 勾上 | JS 读不到，防 XSS 偷会话 |
| `Secure` | ✅ 勾上 | 只在 HTTPS 下传输 |
| `SameSite` | `Lax` | 防 CSRF |
| `Path` | `/` | |

**如果登录成功但立刻又变回未登录**，99% 是 `COOKIE_SECURE=true` 但你在用 HTTP 访问 —— 浏览器直接把这个 Cookie 丢了。要么上 HTTPS，要么临时把 `COOKIE_SECURE` 改回 `false`。

### 8.4 调试接口确实关了

```bash
curl -i https://app.example.com/api/auth/session
# 401（未登录）或 404（已关闭）
```

已登录状态下访问应该是 **404**，说明 `ENABLE_DEBUG_ENDPOINTS=false` 生效了。

### 8.5 数据库端口没暴露

```bash
# 在你自己的电脑上执行，不是服务器
nc -zv 1.2.3.4 3306     # 应该超时/拒绝
nc -zv 1.2.3.4 6379     # 应该超时/拒绝
```

能连上就说明安全组配错了，立刻去关。

### 8.6 主从复制正常

```bash
cd /opt/fullstack-cluster-tutorial/deploy/cloud
set -a; source .env; set +a      # 让下面的 $MYSQL_ROOT_PASSWORD 有值
docker compose --env-file .env -f docker-compose.prod.yml exec mysql-slave \
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW REPLICA STATUS\G" | grep -E "Running|Behind"
```

两个 `Yes` + `Seconds_Behind_Source: 0` 才算正常。

### 8.7 故障演练（重要）

```bash
# 停掉一个副本，看服务是否还正常
docker compose --env-file .env -f docker-compose.prod.yml stop backend-2
curl -s https://app.example.com/api/system/health   # 仍然 200
docker compose --env-file .env -f docker-compose.prod.yml start backend-2
```

Nginx 会在 `max_fails=3` 次失败后把 `backend-2` 摘掉，10 秒后再试探。这个过程**用户几乎无感** —— 这就是多副本的意义。

## 9. 备份与恢复

### 9.1 手动备份

```bash
bash scripts/cloud/backup.sh
```

会在项目根生成 `backups/`：

```
backups/
├── mysql-20261103-031000.sql.gz
└── redis-20261103-031000.rdb
```

### 9.2 定时备份

```bash
sudo crontab -e
```

加一行（每天凌晨 3:10）：

```
10 3 * * * /opt/fullstack-cluster-tutorial/scripts/cloud/backup.sh >> /var/log/app-backup.log 2>&1
```

脚本会自动删除超过 `BACKUP_KEEP_DAYS`（默认 7 天）的旧文件。

> ⚠️ **本地备份只防「误删数据」，不防「整台机器没了」**。
> 真想安全，必须异地：把 `BACKUP_TO_COS=true` 打开，配合腾讯云 COS + `coscli`，备份会自动同步到对象存储。

### 9.3 恢复演练（一定要做一次）

备份不做恢复演练等于没有备份。找个月黑风高的时间练一遍：

```bash
cd /opt/fullstack-cluster-tutorial
set -a; source deploy/cloud/.env; set +a    # 后面要用到 $MYSQL_ROOT_PASSWORD

# 1) 停应用，避免写入
docker compose --env-file deploy/cloud/.env -f deploy/cloud/docker-compose.prod.yml stop backend-1 backend-2 backend-3

# 2) 导入
gunzip -c backups/mysql-20261103-031000.sql.gz | \
  docker compose --env-file deploy/cloud/.env -f deploy/cloud/docker-compose.prod.yml \
  exec -T mysql-master mysql -uroot -p"$MYSQL_ROOT_PASSWORD"

# 3) 重启应用
docker compose --env-file deploy/cloud/.env -f deploy/cloud/docker-compose.prod.yml \
  start backend-1 backend-2 backend-3
```

## 10. 监控：先做最便宜的三件事

不用一上来就上 Prometheus + Grafana。按性价比排序：

### ① 云监控告警（免费，5 分钟配好）

腾讯云控制台 → 云监控 → 告警策略，配三条：

- CPU 使用率 > 80% 持续 5 分钟
- 内存使用率 > 85% 持续 5 分钟
- **磁盘使用率 > 80%** ← 最容易出事的一条

告警方式选微信/短信。

### ② 外部可用性监控（免费）

用任意 uptime 服务（如 UptimeRobot）监控 `https://app.example.com/api/system/health`，1 分钟一次，挂了发邮件。

这比任何内部监控都直接：**用户能不能打开，才是唯一标准**。

### ③ 日志

```bash
cd /opt/fullstack-cluster-tutorial/deploy/cloud
alias dc='docker compose --env-file .env -f docker-compose.prod.yml'

dc logs -f --tail=100 backend-1
dc logs --tail=200 lb            # 看 Nginx 访问日志和 upstream
```

Nginx 的日志格式里带了 `up=$upstream_addr`，能直接看出每个请求落到了哪个副本：

```
1.2.3.4 - [03/Nov/2026:10:12:33 +0800] "GET /api/notes HTTP/2.0" 200 431 up=172.18.0.5:8000 rt=0.012
```

## 11. 什么时候该扩容

先别急着加机器，按这个顺序判断：

| 现象 | 先做什么 | 再做什么 |
| --- | --- | --- |
| CPU 偶尔飙高 | 看是不是构建/备份撞一起了 | 错开时间 |
| 内存吃紧 | 关掉不用的服务；MySQL 调小 buffer pool | 升配置（纵向） |
| 数据库慢查询多 | 加索引、看慢日志 | 拆到 TencentDB |
| 应用 QPS 高 | 加后端副本（改 compose 加 backend-4） | 多机 + CLB |
| 单机不够用了 | 把 MySQL 换成腾讯云数据库 TencentDB | 应用无状态，随便扩 |

**关键前提**：因为 Session 在 Redis、应用本身无状态，**加副本就是改一行 compose 再部署**，不需要改代码。这正是前面几章折腾「集中式 Session」的回报。

### 进阶路线

1. **镜像仓库**：把镜像推到腾讯云 TCR，服务器只 `pull` 不 `build`，部署从 8 分钟降到 1 分钟。
   ```dotenv
   IMAGE_PREFIX=ccr.ccs.tencentyun.com/你的命名空间/
   USE_PREBUILT_IMAGE=true
   ```
2. **多机 + CLB**：两台 CVM 各跑一份 compose，前面挂腾讯云负载均衡 CLB。
3. **托管数据库**：MySQL 换 TencentDB（自动主从、自动备份、自动故障切换），Redis 换云数据库 Redis。
4. **容器平台**：迁到 TKE（Kubernetes），滚动更新、自动扩缩容、健康检查全都交给平台。

## 12. 排障手册

部署出问题时，先按「错误信息」查这张表：

| 错误信息 / 现象 | 原因 | 解决 |
| --- | --- | --- |
| `$'\r': command not found` | Windows 换行符 | `sed -i 's/\r$//' scripts/cloud/*.sh` |
| `.env 里还有 CHANGE_ME` | 忘了改模板 | 编辑 `.env`，搜 `CHANGE_ME` 全部替换 |
| `bind: address already in use` (80) | 宿主机已有 Nginx/Apache | `sudo systemctl stop nginx apache2`，或改端口 |
| `cannot load certificate` | `certs/` 下没有证书 | 删掉空的 `certs` 目录重跑 `deploy.sh`（会生成自签） |
| 502 Bad Gateway | 后端没起来 / 连不上数据库 | `dc logs backend-1`；再 `dc ps` 看是否 healthy |
| 登录成功但立刻退出 | `COOKIE_SECURE=true` 却用 HTTP 访问 | 上 HTTPS；或临时改 `false` |
| `Access denied for user 'appuser'` | 改了 `.env` 密码，但数据库卷是旧的 | 见下方「改密码的正确姿势」 |
| `Unknown database 'fullstack_demo'` | 从库还没同步完 | 等 1~2 分钟；或查 `SHOW REPLICA STATUS` |
| 页面白屏，接口 404 | Nginx 模板没生效 | `dc logs lb` 看是否 `envsubst` 报错；确认 `DOMAIN` 有值 |
| 磁盘满 `No space left on device` | 镜像/日志/备份堆积 | `docker system prune -af`；清理 `backups/` |
| `Killed`（构建时） | 内存不足 | 确认 swap 生效：`free -h` |
| SSH 连不上 | 安全组/防火墙改错 | 用控制台 VNC 登录，检查 `ufw status` |

### 改密码的正确姿势

这是**最高频的坑**：MySQL 只在「数据目录为空」时用 `MYSQL_ROOT_PASSWORD` 初始化。如果你已经部署过、数据卷里有数据，再改 `.env` 里的密码，**完全不生效**，因为旧密码已经写进 `mysql.user` 表了。

三种解法，按推荐度排序：

**① 进容器手动改（不丢数据）**

```bash
dc exec mysql-master mysql -uroot -p'旧密码' -e "
  ALTER USER 'appuser'@'%' IDENTIFIED BY '新密码';
  ALTER USER 'root'@'localhost' IDENTIFIED BY '新根密码';
  FLUSH PRIVILEGES;"
# 然后改 .env，再 dc up -d
```

**② 重建（丢数据，仅测试环境）**

```bash
dc down -v          # -v 会删数据卷，谨慎
bash scripts/cloud/deploy.sh
```

**③ Redis 的密码不同**：Redis 密码只是配置项，`deploy.sh` 检测到 `redis.conf` 变化会自动重启 redis，改完直接生效 ✅。

## 15. 本章小结

你刚刚完成的，是一次完整的「从开发到上线」闭环：

```
写代码 → 容器化 → 编排 → 密钥外置 → HTTPS → 一键部署
                              ↓
                        健康检查 + 自动回滚
                              ↓
                        备份 + 监控 + 排障手册
```

**记住三个最重要的点**：

1. **密码永远不进代码仓库**，用 `.env` + 600 权限 + 随机值。
2. **部署必须有健康检查和回滚**，否则一次失败的发布会让你半夜爬起来手动救。
3. **安全组是最外层防线**，数据库端口一刻都不要对公网开放。

### 练习题

1. 把 `backend-3` 停掉，观察 Nginx 多久把它摘除、恢复后又多久重新纳入（看 `dc logs lb`）。
2. 修改 `.env` 里的 `SESSION_TTL_SECONDS=60`，重新部署，登录后等 1 分钟，看页面会不会自动跳回登录页。
3. 用 `rollback.sh` 回到上一版，再用 `deploy.sh` 发一次新版，观察 `.current-tag` 和 `.previous-tag` 的变化。
4. 把 `IMAGE_PREFIX` 指向腾讯云 TCR，试试「服务器只拉镜像、不构建」的部署方式，对比耗时差异。
