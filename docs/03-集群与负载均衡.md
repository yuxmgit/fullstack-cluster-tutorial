# 03 · 集群与负载均衡：领班是怎么派单的

> 对应代码：`deploy/docker-compose.yml`、`deploy/nginx-lb.conf`、`backend/app/routers/system.py`

---

## 3.1 为什么要「集群」

单台服务器会遇到三个天花板：

| 问题 | 表现 | 单机怎么救 | 集群怎么救 |
| --- | --- | --- | --- |
| 性能不够 | 并发一高响应变慢 | 加 CPU / 内存（**垂直扩容**） | 多开几台（**水平扩容**） |
| 会挂 | 进程崩了、机器断电，全站 502 | 只能靠重启，仍然中断 | 一台挂了，其余继续服务 |
| 发布要停机 | 更新代码得停服务 | 半夜停机维护 | 滚动更新，逐台替换 |

垂直扩容很快到顶（硬件贵、有上限、且**单点故障没解决**）。水平扩容才是现代架构的主线，但它有一个硬前提：

> **后端必须是「无状态」的。**

## 3.2 「无状态」到底指什么

不是「不用数据库」，而是：**任何一个后端副本，处理任何一次请求，都不依赖自己本地留存的东西。**

检查清单（每项都是真实踩过的坑）：

| 有状态的东西 | 集群下的后果 | 改造方式 |
| --- | --- | --- |
| 登录 Session 存进程内存 | 掉登录（第 02 章实验 1） | → Redis 集中式 Session ✅ 本项目已做 |
| 验证码存全局变量 | 生成在 A、校验到 B，永远失败 | → Redis，带 TTL |
| 上传文件存本地磁盘 | 上传到 A，从 B 下载 404 | → 对象存储 / 共享 NFS ✅ 见 07 章 |
| 本地缓存（字典 / lru_cache） | 各副本数据不一致 | → Redis 共享缓存，或接受短暂不一致 |
| 定时任务（每副本都跑） | 邮件发 3 遍、报表重复 | → 分布式锁 / 独立任务服务 ✅ 本项目用 Redis 锁做启动初始化 |
| WebSocket 连接 | 连接绑在某台，广播要跨机 | → Redis Pub/Sub / 专门网关 |
| 本地自增 ID / 本地计数器 | 重复或错乱 | → 数据库自增 / Redis INCR / 雪花 ID |
| 依赖「我是第几台」的配置 | 扩容时忘了改 | → 配置中心 / 环境变量 |

**本项目怎么证明自己无状态**：`backend/app/routers/system.py` 返回 `instance_id`（容器主机名）。你刷新页面，它在 `backend-1/2/3` 之间跳，而登录态、留言数据、会话计数**完全不变**。能承受「随便换人接手」就是无状态。

> 顺带一提：`instance_id`、``hits`` 这类信息我们特意**放到 Redis/数据库**里，而不是进程内存里，
> 所以「请求计数」是全局累加的，你在任何副本上看到的都是同一个数 —— 这本身就是无状态设计的示范。

## 3.3 负载均衡器（领班）站在哪儿

```
              用户（只知道一个地址）
                      │
                      ▼
        ┌─────────────────────────┐
        │  Nginx  ← 这一层叫 LB     │  ← 反向代理 + 负载均衡
        │  · 统一入口（隐藏后端）    │
        │  · 决定派给哪台           │
        │  · 健康检查、摘除故障节点  │
        │  · 顺手做静态资源、HTTPS   │
        └──────┬──────┬──────┬────┘
               ▼      ▼      ▼
            be-1   be-2   be-3     ← 上游 upstream，彼此不知道对方存在
```

**反向代理 vs 正向代理**（容易混）：

- 正向代理：替**客户端**出去（科学上网、公司代理），服务器不知道真实客户端；
- 反向代理：替**服务器**接客，客户端不知道真实后端。Nginx 在这里是反向代理。

负载均衡可以有很多层：

| 层 | 例子 | 说明 |
| --- | --- | --- |
| DNS 级 | 多 A 记录、智能 DNS | 粗粒度，切换慢 |
| 四层（TCP/UDP） | LVS、HAProxy、云 CLB | 性能好，不看 HTTP 内容 |
| **七层（HTTP）** | **Nginx、HAProxy、云 ALB** | 能按 URL、Header、Cookie 分流 ← 本项目 |
| 服务网格 / K8s | Ingress、Service、Envoy | 容器编排里自动做 |

## 3.4 Nginx upstream：本项目配置逐行读

`deploy/nginx-lb.conf`：

```nginx
upstream backend_pool {
    # 默认就是 round-robin 轮询：1 → 2 → 3 → 1 ...
    server backend-1:8000 max_fails=3 fail_timeout=10s;
    server backend-2:8000 max_fails=3 fail_timeout=10s;
    server backend-3:8000 max_fails=3 fail_timeout=10s;
    keepalive 32;                       # 与后端保持长连接，减少握手开销
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://backend_pool;
        proxy_http_version 1.1;
        proxy_set_header Connection "";         # 配合 keepalive
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For  $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
    }

    location / {
        proxy_pass http://frontend:80;
    }
}
```

几个关键点：

- `backend-1:8000` 用的是 **Docker Compose 的服务名**，容器 DNS 自动解析，不用写 IP；
- `max_fails=3 fail_timeout=10s`：**被动健康检查**。某台连续失败 3 次，Nginx 暂时 10 秒不派单给它；之后会再试探。这就是「一台挂了不影响全站」；
- `X-Forwarded-For` 必须透传，否则后端看到的客户端 IP 全是 Nginx 的，日志和风控全废。本项目 `backend/app/routers/auth.py` 里的 `client_ip()` 会优先读这个头；
- `location /api/` 只转发 API，`location /` 转发前端静态资源 —— **一个域名、两种后端**，这就是 01 章说的「同源」的实现。

### 四种分发策略

| 策略 | 配置 | 效果 | 适用 |
| --- | --- | --- | --- |
| 轮询 | 默认 | 依次 1-2-3 | 请求耗时接近、后端配置相同 ✅ 本项目 |
| 加权轮询 | `server backend-1:8000 weight=3;` | 强者多干 | 机器配置不一样 / 灰度发布 |
| 最少连接 | `least_conn;` | 派给当前最闲的 | 请求耗时差异大（有长任务） |
| IP 哈希 | `ip_hash;` | 同一 IP 永远同一台 | **粘性会话**、WebSocket；缺点见 2.4 |
| 一致性哈希 | `hash $request_uri consistent;` | 同类请求落同一台 | 缓存命中率优化 |

> 本项目特意用**默认轮询**：因为它最能暴露「有状态」的 bug，也最能验证 Redis Session 的价值。
> 换成 `ip_hash`，实验 1 反而「看起来正常」，会掩盖问题 —— 这正是很多人在本机测不出问题、上线才炸的原因。

## 3.5 健康检查：两种，别搞混

| 类型 | 谁发起 | 本项目 |
| --- | --- | --- |
| **被动检查** | Nginx 发现转发失败才标记 | ✅ `max_fails` / `fail_timeout` |
| **主动检查** | LB 定时请求 `/healthz`（开源版 Nginx 需 `nginx_upstream_check_module`，或用云 LB / HAProxy） | ✅ 后端提供 `/api/system/health` + compose `healthcheck` |

本项目在 compose 里给每个后端加了：

```yaml
healthcheck:
  test: ["CMD", "python", "-c", "import urllib.request;urllib.request.urlopen('http://localhost:8000/api/system/health')"]
  interval: 10s
  timeout: 3s
  retries: 3
```

`depends_on: condition: service_healthy` 保证 Nginx / 依赖方在后端真正可用后才启动，避免启动时一堆 502。

> 健康检查接口要**只检查自身进程**，别在里面查数据库 —— 否则数据库一抖，所有后端被同时判死，全站雪崩。

## 3.6 集群带来的「新麻烦」（比负载均衡本身更重要）

| 新问题 | 说明 | 本项目怎么处理 |
| --- | --- | --- |
| 谁来做初始化 | 3 个副本同时启动，都去 `CREATE TABLE` / 插初始用户会冲突 | `database.py` 用 Redis `SET init:lock NX EX 30` 抢锁，只让一个副本执行 |
| 日志散落 | 出问题要登 3 台机器查日志 | 全部打到 stdout，用 `docker compose logs` 统一看（生产上 ELK / Loki） |
| 配置不一致 | 改了 A 忘了 B | 全部走**环境变量**，compose 里用 YAML 锚点复用同一份配置 |
| 请求追踪 | 一次请求跨多服务，不知道在哪一步慢 | 加 `X-Request-ID` 并在日志里带上（07 章） |
| 会话亲和 | WebSocket、大文件分片上传 | 用对象存储 / Redis PubSub，别用 ip_hash 硬扛 |
| 发布时间差 | 滚动更新时新旧版本并存 | 接口向后兼容、数据库迁移先于应用发布 |
| LB 自己成了单点 | Nginx 挂了全站完蛋 | 生产：2 台 Nginx + Keepalived VIP，或直接用云负载均衡 |

### 本项目里的「启动锁」值得单独看

`backend/app/database.py`：

```python
def init_schema_and_seed():
    if settings.SESSION_BACKEND == "redis":
        got = redis.set("init:schema:lock", os.getenv("INSTANCE_ID", "local"), nx=True, ex=30)
        if not got:
            return "skipped: another replica is initializing"   # 没抢到锁，直接跳过
    try:
        Base.metadata.create_all(bind=write_engine)             # 建表
        seed_users(write_engine)                                # 插初始账号
    finally:
        ...
```

这是一切「集群里只能执行一次」的任务的通用套路：**分布式锁**。定时任务、缓存预热、数据迁移都用它。锁的 TTL 要大于任务耗时，并且要考虑任务失败后锁自动释放。

## 3.7 一次扩缩容的完整动作

想从 3 副本扩到 5 副本，在本项目里只需要：

1. compose 里加 `backend-4`、`backend-5`（复用同一份 YAML 锚点）；
2. `nginx-lb.conf` 的 upstream 里加两行；
3. `docker compose up -d --scale`（或重启 lb）。

**前端一行不用改，后端代码一行不用改，用户无感知。** 这就是无状态 + 集中式 Session 换来的自由度。

生产环境不会手工改文件，而是用 K8s `Deployment` 的 `replicas: 5` + `Service` 自动服务发现，或者云厂商的弹性伸缩组。但底层道理完全相同。

> 反过来，如果当初把 Session 放内存，扩到 5 台意味着用户登录成功率从 1/3 掉到 1/5 —— 加机器反而让体验变差，这就是最反直觉、也最值得记住的一点。

## 3.8 小结与动手任务

- 集群 = 多台相同副本 + 一个负载均衡器，目的是容量、高可用、可滚动发布；
- 前提是**后端无状态**，把所有本地状态外移到 Redis / DB / 对象存储；
- Nginx `upstream` 默认轮询，配合 `max_fails` 做被动摘除，配合 `X-Forwarded-*` 透传真实信息；
- 集群会引入「初始化只跑一次、日志、配置、追踪、发布」等新问题，都要有对应机制。

**动手任务**

1. 跑 `scripts/verify-cluster.ps1`，看 12 次请求是不是均匀落到 3 个副本；
2. `docker stop <backend-2容器名>`，再刷新几次，确认网站仍可用（Nginx 把故障节点摘了）；再 `docker start` 恢复；
3. 把 `nginx-lb.conf` 改成 `least_conn;` 或给 `backend-1` 加 `weight=3`，`docker compose restart lb`，观察分布变化；
4. 试试加 `ip_hash;`，重做 02 章实验 1 —— 你会发现「掉登录」被掩盖了。思考：这算修好了吗？（不算，只是把问题藏起来了）
5. 把 `backend-3` 从 upstream 注释掉，只留 2 台，体会「改配置即缩容」。
