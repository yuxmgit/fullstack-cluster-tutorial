# 01 · 前后端分离与跨域：为什么本地好好的，一部署就报错

> 对应代码：`frontend/src/api/index.js`、`frontend/vite.config.js`、`backend/app/main.py`、`deploy/nginx-lb.conf`

---

## 1.1 先搞清楚「不分离」长什么样

早期网站是这样工作的（以 Python 的 Jinja 模板为例）：

```python
# 伪代码：服务端直接把数据塞进 HTML
@app.get("/notes")
def notes_page():
    notes = db.query("SELECT * FROM note")
    return render_template("notes.html", notes=notes, username="alice")
```

浏览器请求一个地址，服务器返回**一整张已经填好数据的 HTML**。页面长什么样、数据是什么，全是后端决定的。

特点：

- 后端要管 HTML/CSS，前端改个按钮颜色都得求后端发版；
- 每次点链接都要整页刷新；
- 但**没有跨域问题**，因为只有一个服务器、一个域名。

## 1.2 「分离」到底分的是什么

分离之后，两边各干各的，靠一份**接口约定（契约）**合作：

```
前端（Vue）                          后端（Python）
─────────────                        ─────────────
负责：页面结构、样式、交互、路由        负责：校验、业务规则、数据库读写
产物：一堆静态文件 (html/js/css)      产物：一串 JSON
部署：随便扔到 CDN / Nginx / 对象存储   部署：跑在服务器上，可开很多份
交流：─────── HTTP + JSON ───────→
     ←────── {code, data, message} ──
```

本项目里的契约长这样（`backend/app/routers/auth.py`）：

| 接口 | 方法 | 请求 | 响应 |
| --- | --- | --- | --- |
| `/api/auth/login` | POST | `{username, password}` | `{ok, user}` + Set-Cookie |
| `/api/auth/me` | GET | 自动带 Cookie | `{user, session, handled_by}` |
| `/api/notes` | GET | 自动带 Cookie | `{items: [...], db_role}` |
| `/api/notes` | POST | `{title, content}` | 新建的留言 |

> **关键认知**：分离之后，前端和后端是**两个独立程序**，可以分别开发、分别部署、分别扩容。
> 前端甚至不知道后端有几台机器、用什么语言写的。
> 这也是为什么后面能把后端从 1 台扩到 3 台而前端一行代码都不用改。

**好处**：并行开发、前端秒开（静态资源可上 CDN）、后端可专注性能与安全、一套 API 能同时服务网页/App/小程序。
**代价**：多了一个跨域问题，多了一套登录态传递机制（这正是第 02 章的主题），SEO 需要额外处理。

## 1.3 跨域（CORS）：本教程第一个拦路虎

### 1.3.1 什么是「同源」

浏览器判断两个地址是否同源，只看三样东西：**协议 + 域名 + 端口**，三者完全一致才算同源。

| 当前页面 | 请求地址 | 同源？ | 原因 |
| --- | --- | --- | --- |
| `http://localhost:5173` | `http://localhost:5173/api/x` | ✅ | 全一样 |
| `http://localhost:5173` | `http://localhost:8000/api/x` | ❌ | **端口不同** |
| `http://localhost:8080` | `http://127.0.0.1:8080/api/x` | ❌ | 域名不同（`localhost` ≠ `127.0.0.1`） |
| `https://a.com` | `http://a.com/api/x` | ❌ | 协议不同 |
| `https://a.com` | `https://b.a.com/api/x` | ❌ | 子域名不同 |

**同源策略**：浏览器默认不允许「A 来源的 JS 读取 B 来源的响应」。注意是**浏览器**在拦，服务器其实已经正常返回了。用 `curl`、Postman、后端之间互相调用，全都不受限制。

> 为什么要拦？想象你打开 `evil.com`，它的 JS 偷偷请求 `bank.com/transfer`，
> 如果浏览器不拦，而你的银行 Cookie 又自动带上了，钱就没了。

### 1.3.2 CORS：服务端主动「放行」

后端在响应里加几个头，浏览器就放行：

```
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: Content-Type
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
```

本项目 `backend/app/main.py`：

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.CORS_ORIGINS,   # 明确列出，不要用 ["*"]
    allow_credentials=True,               # 允许携带 Cookie（登录必须用）
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**两条铁律**：

1. 需要带 Cookie 时，`allow_origins` **不能写 `"*"`**，必须写具体域名，且必须 `allow_credentials=True`；
2. 前端 axios 必须配 `withCredentials: true`（本项目 `frontend/src/api/index.js` 已配）。两边缺一不可。

### 1.3.3 预检请求 OPTIONS

当请求「不简单」（比如 `POST` + `Content-Type: application/json`、自定义头），浏览器会**先发一个不带数据的 OPTIONS** 问一句「我能这么干吗」，得到允许后才发真正的请求。

```
浏览器 → OPTIONS /api/auth/login       （预检：我要 POST + JSON 头，行吗）
服务器 → 200 OK + Allow-* 头           （行）
浏览器 → POST   /api/auth/login {...}  （真请求）
```

所以后端日志里凭空多出一个 OPTIONS 不要慌。FastAPI 的 `CORSMiddleware` 会自动处理，你不用写任何 OPTIONS 路由。

### 1.3.4 三种解决办法，以及各自用在哪

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **CORS 放行** | 后端加响应头 | 最简单，前后端域名各自独立 | 要维护白名单；Cookie 受 SameSite 限制 | 前后端不同域名（如 `api.example.com` + `www.example.com`） |
| **开发代理** | Vite / webpack 把 `/api` 转发给后端 | 浏览器看到的是同源，**零 CORS 配置** | 只用于开发 | 本地写代码 |
| **反向代理同域** | Nginx：`/` → 前端，`/api/` → 后端 | 生产最优：同源、Cookie 好管、后端不暴露、能顺手做负载均衡 | 多一层 Nginx | ✅ **生产推荐，本项目采用** |

### 1.3.5 本项目是怎么做的

**开发时**（`frontend/vite.config.js`）：

```js
server: {
  port: 5173,
  proxy: {
    '/api': {
      target: 'http://localhost:8000',
      changeOrigin: true,
    },
  },
}
```

浏览器访问 `http://localhost:5173`，JS 里写 `axios.get('/api/auth/me')`，实际请求的是 `http://localhost:5173/api/auth/me`，由 **Vite（Node 服务端）** 转发到 8000。浏览器从头到尾只跟 5173 打交道 → 同源 → 不需要 CORS。

**生产时**（`deploy/nginx-lb.conf`）：

```nginx
server {
    listen 80;

    location /api/ {
        proxy_pass http://backend_pool;      # 转发给后端集群
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://frontend:80;       # 转发静态页面
    }
}
```

浏览器只访问 `http://localhost:8080`。`/` 拿页面，`/api/` 拿数据，**同一个域名** → 同源 → 同样不需要 CORS。

> 那 `backend/app/main.py` 里的 CORS 还有用吗？有：本地开发时如果你直接用 `http://localhost:5173` 去请求 `http://localhost:8000`（不走代理），或者将来把 API 拆到独立域名，就需要它。**留着是兜底和教学演示**。

**一句话总结**：生产环境让 Nginx 把前后端合成「一个域名」，跨域问题就**从根上消失了**，而不是靠一堆响应头去绕。这也是为什么大厂线上几乎都是 `www.xxx.com` + `/api` 这种形式。

## 1.4 Cookie 的几个属性（登录态全靠它，必须懂）

登录成功后后端返回：

```
Set-Cookie: session_id=K8sdf...; HttpOnly; SameSite=Lax; Path=/; Max-Age=1800
```

| 属性 | 作用 | 本项目取值 | 不设会怎样 |
| --- | --- | --- | --- |
| `HttpOnly` | JS 读不到这个 Cookie | 开启 | XSS 攻击能直接偷走会话号 |
| `Secure` | 只在 HTTPS 下发送 | 本地关、生产开 | HTTP 环境下 Cookie 根本发不出去（新手常踩） |
| `SameSite` | 控制跨站请求带不带 Cookie | `Lax` | 设 `None` 必须配 `Secure`；设 `Strict` 会让从外站跳回来时掉登录 |
| `Path=/` | 整个站点都带上 | `/` | `/api` 下才带，前端页面拿不到 |
| `Max-Age` | 浏览器端有效期（秒） | 1800 | 关掉浏览器就失效 |
| `Domain` | 哪些域名可见 | 不设（默认当前域） | 设错会导致子域共享或完全不带 |

> 本项目在 `backend/app/routers/auth.py` 里用 `response.set_cookie(...)` 设置。
> `COOKIE_SECURE` 环境变量控制 `Secure`，本地 HTTP 必须为 `False`，上 HTTPS 时改成 `True`。

**重要认知**：Cookie 里只放一个**随机号码牌（session_id）**，不放用户名、不放权限、更不放密码。
真正的用户档案在 Redis 里。浏览器拿不到、也改不了档案内容 —— 这比把用户信息明文塞 Cookie 安全得多，也是第 02 章的核心。

## 1.5 前端要配合的三件事

`frontend/src/api/index.js`：

```js
const api = axios.create({
  baseURL: '/api',        // 相对路径！不写死域名，开发/生产都能用
  withCredentials: true,  // 带上 Cookie
  timeout: 10000,
})

// 统一处理 401：登录过期就跳登录页
api.interceptors.response.use(
  (res) => res.data,
  (err) => {
    if (err.response?.status === 401) {
      localStorage.removeItem('user_hint')
      window.location.href = '/login'
    }
    return Promise.reject(err)
  }
)
```

`frontend/src/router/index.js` 用路由守卫做「页面级」拦截，但因为守卫无法同步知道服务端 Session 是否有效，所以 `main.js` 启动时还会主动调一次 `/api/auth/me` 以服务端为准。

> **经验**：前端保存的「我登录了」只能是**缓存/展示用**，真正的判定永远以服务端 `/api/auth/me` 为准。
> 因为用户可能在别的标签页登出、Session 可能过期、也可能被管理员踢下线。

## 1.6 报错排查清单

| 现象 | 大概率原因 | 怎么修 |
| --- | --- | --- |
| `Access to fetch ... has been blocked by CORS policy` | 后端没配 CORS 或白名单不含当前域名 | 检查 `CORS_ORIGINS`；或改用 Vite proxy / Nginx 同域 |
| `Credentials flag is 'true', but Access-Control-Allow-Origin is '*'` | 带了 Cookie 却用了通配源 | 改成具体域名 + `allow_credentials=True` |
| 登录接口返回 200，但之后 `/api/auth/me` 一直 401 | Cookie 没种上：`Secure=True` 但用的是 HTTP；或 `SameSite` 太严；或前端没 `withCredentials` | 本地把 `COOKIE_SECURE=False`，检查 4.1 的属性表 |
| 预检 OPTIONS 返回 405 | 自己写了只接受 GET/POST 的中间件挡住 OPTIONS | 交给 `CORSMiddleware` 处理 |
| 本地能跑，Docker 里前端请求 404 | 前端把 `baseURL` 写成了 `http://localhost:8000` | 改成相对路径 `/api`，让 Nginx 转发 |
| `X-Forwarded-For` 拿不到真实 IP | Nginx 没透传头 | 加 `proxy_set_header`（本项目已配） |

## 1.7 小结与动手任务

- 前后端分离 = 两个独立程序 + 一份 JSON 接口契约；
- 跨域是**浏览器**的安全策略，服务端之间不存在；
- 生产最优解是 **Nginx 反向代理做成同源**，顺便获得负载均衡能力；
- Cookie 里只放随机 `session_id`，靠 `HttpOnly / SameSite / Secure` 保护。

**动手任务**

1. 在浏览器 F12 → Network，找到 `/api/auth/login`，看看 Response Headers 里的 `Set-Cookie`，逐个对照 1.4 的属性表；
2. 把 `frontend/src/api/index.js` 的 `withCredentials` 改成 `false`，刷新，观察是否掉登录（改回来）；
3. 把 `backend/app/main.py` 的 `allow_credentials` 改成 `False`，再用 `http://localhost:8000/docs` 直接调接口，看浏览器控制台报什么错；
4. 试着把 `baseURL` 改成 `http://localhost:8000/api`，在 F12 里亲眼看到一次 CORS 报错（改回来）。
