# 06 · 部署实战与验证：一条命令起整套集群

> 对应文件：`deploy/docker-compose.simple.yml`、`deploy/docker-compose.yml`、`scripts/verify-cluster.ps1`

这一章是「操作手册」。前面的概念如果还有模糊，跑一遍这里就通了。

---

## 6.1 前置检查（Windows / PowerShell）

```powershell
docker --version           # 建议 Docker Desktop 4.x+
docker compose version     # 注意是 v2 的 `docker compose`，不是老的 `docker-compose`
docker info                # 确认 Docker Engine 正在运行
```

必备：Docker Desktop 已启动、内存至少分 4 GB（MySQL ×2 + Redis + 3 个 Python 大约吃 1.5~2 GB）。

端口占用检查（如果被占用，改 compose 里的左侧端口即可）：

```powershell
Get-NetTCPConnection -LocalPort 8080,3306,6380,6379,3307,3308 -ErrorAction SilentlyContinue |
  Select-Object LocalPort, OwningProcess
```

## 6.2 第一步：单机最小版（先成功，再复杂）

```powershell
cd i:/work-body-dir/fullstack-cluster-tutorial
docker compose -f deploy/docker-compose.simple.yml up -d --build
```

`up -d --build` 的意思：`up` 创建并启动、`-d` 后台运行、`--build` 现场构建镜像（改过代码一定要带）。

它会起 5 个服务：

| 服务 | 镜像/构建 | 作用 |
| --- | --- | --- |
| `lb` | nginx:alpine | 统一入口 `localhost:8080`，转发 `/` 和 `/api/` |
| `frontend` | `frontend/Dockerfile` 多阶段构建 | Vue 编译后的静态文件 |
| `backend` | `backend/Dockerfile` | 1 个 FastAPI |
| `mysql` | mysql:8.0 | 单库，读写都走它 |
| `redis` | redis:7-alpine | 集中式 Session |

看启动状态：

```powershell
docker compose -f deploy/docker-compose.simple.yml ps
docker compose -f deploy/docker-compose.simple.yml logs -f backend
```

等到 backend 日志出现 `Application startup complete`，打开 **<http://localhost:8080>**，用 `alice / 123456` 登录。

> 第一次构建要拉镜像、装 pip/npm 依赖，可能 2~5 分钟，属正常。之后会走缓存，几秒钟。

**这一步你要确认的 4 件事**：

1. 登录能成功，页面显示「欢迎 alice」；
2. 发一条留言，刷新后还在（数据进了 MySQL）；
3. F12 → Application → Cookies，能看到 `session_id`，且 `HttpOnly` 打勾；
4. F12 → Network，所有请求都是 `http://localhost:8080/...`，**没有任何跨域报错**。

关掉：

```powershell
docker compose -f deploy/docker-compose.simple.yml down          # 停并删容器（保留数据卷）
docker compose -f deploy/docker-compose.simple.yml down -v       # 连数据卷一起删，彻底重来
```

## 6.3 第二步：完整集群版

```powershell
# 确保没把实验 1 的环境变量留着
Remove-Item Env:SESSION_BACKEND -ErrorAction SilentlyContinue

docker compose -f deploy/docker-compose.yml up -d --build
```

服务清单（8 个）：

| 服务 | 说明 | 端口（宿主→容器） |
| --- | --- | --- |
| `lb` | Nginx 负载均衡 | `8080:80` |
| `frontend` | Vue 静态资源 | 仅内部 |
| `backend-1/2/3` | 3 个相同的 FastAPI，`hostname` 分别是 `backend-1` 等 | 仅内部 `8000`；`backend-1` 额外暴露 `8001→8000` 便于看 `/docs` |
| `redis` | Session + 启动锁 + 全局计数 | `6379:6379` |
| `mysql-master` | 主库（写） | `3307:3306` |
| `mysql-slave` | 从库（读） | `3308:3306` |
| `replica-init` | 一次性任务：配好主从复制，跑完自动退出 | — |

启动顺序由 `depends_on: condition: service_healthy` 保证：MySQL/Redis 健康 → `replica-init` 配复制 → backend（抢启动锁建表）→ lb。

```powershell
docker compose -f deploy/docker-compose.yml ps
# replica-init 显示 Exit 0 是正常的，它就是干完就走
```

### compose 里几个值得学的写法

```yaml
x-backend-common: &backend-common      # YAML 锚点：3 个副本共享同一份配置，避免复制粘贴出错
  build: ../backend
  environment: &backend-env
    DB_WRITE_URL: mysql+pymysql://demo:demo123@mysql-master:3306/fullstack_demo
    DB_READ_URL:  mysql+pymysql://demo:demo123@mysql-slave:3306/fullstack_demo
    REDIS_URL:    redis://:redispass@redis:6379/0
    SESSION_BACKEND: ${SESSION_BACKEND:-redis}   # ← 宿主机环境变量可覆盖，实验 1 就靠它
  restart: unless-stopped

services:
  backend-1:
    <<: *backend-common
    hostname: backend-1                # 让 /api/system/info 返回好认的名字
    environment:
      <<: *backend-env
      INSTANCE_ID: backend-1
```

- `<<: *anchor` 是 YAML 合并键，配置复用，改一处全生效；
- `${SESSION_BACKEND:-redis}`：外面不设就用 `redis`，设了就用外面的值；
- 服务名即 DNS 名，`mysql-master`、`redis` 在容器内直接能解析；
- 应用不写死任何 IP，**换环境只改环境变量**。

## 6.4 实验 1：复现「集群掉登录」

```powershell
$env:SESSION_BACKEND = "memory"       # 只影响当前 PowerShell 会话
docker compose -f deploy/docker-compose.yml up -d --build
```

> 注意：`up -d --build` 会重建 backend 容器，因为环境变量变了 compose 会重新创建服务。

打开 <http://localhost:8080>：

1. 用 `alice / 123456` 登录；
2. 连续按 F5 刷新 10 次；
3. 记录每次「本次请求由哪个副本处理」显示的名字，以及是否被踢回登录页。

预期结果（示意）：

| 刷新 | 处理副本 | 登录状态 |
| --- | --- | --- |
| 1 | backend-1 | ✅ 正常（登录就是它处理的） |
| 2 | backend-2 | ❌ 跳登录 |
| 3 | backend-3 | ❌ 跳登录 |
| 4 | backend-1 | ✅ 正常 |
| … | … | 约 1/3 正常 |

**为什么**：`MemorySessionStore` 是进程内字典，`backend-1` 写的档案其它副本看不到（02 章）。

## 6.5 实验 2：切回 Redis，问题消失

```powershell
Remove-Item Env:SESSION_BACKEND
docker compose -f deploy/docker-compose.yml up -d --build
```

登录后：

1. 刷新 20 次 → 副本 id 一直在变，但**始终登录**；
2. 看「会话访问计数」→ 单调 +1，不会因换副本而重置；
3. 打开左侧「架构实验室」→ 能看到 Redis 里的 `sess:*` 原文、剩余 TTL、本次查询走的数据库角色。

这三个现象合起来就是「集中式 Session + 无状态副本」的完整证据链。

### 一键验证脚本

```powershell
.\scripts\verify-cluster.ps1
```

脚本会连续打 12 次 `/api/system/info`，统计每个副本被命中几次，并带上登录态跑一次 `/api/auth/me`，输出类似：

```
[1] backend-2   [2] backend-3   [3] backend-1  ...
副本分布: backend-1=4  backend-2=4  backend-3=4   ← 轮询生效
带会话请求: 200 OK, user=alice, hits=13            ← Session 共享生效
```

## 6.6 实验 3：负载均衡与主从复制

```powershell
# ① 停掉一个副本，确认全站仍可用
docker compose -f deploy/docker-compose.yml stop backend-2
.\scripts\verify-cluster.ps1          # 请求只落到 1、3，无 5xx
docker compose -f deploy/docker-compose.yml start backend-2

# ② 查主从复制状态
docker compose -f deploy/docker-compose.yml exec mysql-slave `
  mysql -uroot -prootpass -e "SHOW REPLICA STATUS\G" | Select-String "Running|Behind|Error"

# ③ 网页上新建留言，比对主库/从库条数
docker compose -f deploy/docker-compose.yml exec mysql-master `
  mysql -uroot -prootpass fullstack_demo -e "SELECT COUNT(*) AS master_count FROM notes;"
docker compose -f deploy/docker-compose.yml exec mysql-slave `
  mysql -uroot -prootpass fullstack_demo -e "SELECT COUNT(*) AS slave_count FROM notes;"

# ④ 停掉从库，看读降级
docker compose -f deploy/docker-compose.yml stop mysql-slave
# 刷新页面 → 「架构实验室」里 db_role 显示 primary(fallback)，功能正常
docker compose -f deploy/docker-compose.yml start mysql-slave
```

> 从库刚起来时复制可能要几秒才追上，`Seconds_Behind_Source` 会短暂 >0，这正好演示 04 章说的复制延迟。

## 6.7 排查手册

| 症状 | 命令 | 检查什么 |
| --- | --- | --- |
| 页面打不开 | `docker compose -f deploy/docker-compose.yml ps` | `lb` 是否 Up、8080 是否映射 |
| 前端 502 | `docker compose ... logs lb` | upstream 里后端是否 healthy |
| 一直跳登录 | `docker compose ... logs backend-1 --tail=50` | `SESSION_BACKEND` 是不是被设成 memory、Redis 是否可达 |
| 数据库连不上 | `docker compose ... logs mysql-master` | 是否还在初始化（首次约 20~40 秒） |
| 从库不同步 | `SHOW REPLICA STATUS\G` | `Last_IO_Error` / `Last_SQL_Error`；`replica-init` 是否 Exit 0 |
| 改了代码没生效 | `docker compose ... up -d --build` | 是否忘了 `--build` / 浏览器缓存（Ctrl+F5） |
| 前端改了没生效 | 同上 | `frontend` 是多阶段构建，必须重新 build 镜像 |

**万能三连**：

```powershell
docker compose -f deploy/docker-compose.yml down -v      # 全清
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml logs -f      # 盯日志
```

### 直接调接口（不经过前端，定位问题特别快）

```powershell
# FastAPI 自带文档，可视化调所有接口
# 集群版只把 backend-1 的 8000 映射到宿主机的 8001，方便学习时直接调接口
start http://localhost:8001/docs

# 用 curl 走统一入口，并手动带 Cookie
curl.exe -i -X POST http://localhost:8080/api/auth/login `
  -H "Content-Type: application/json" `
  -d '{\"username\":\"alice\",\"password\":\"123456\"}'

# 复制上面响应里的 session_id，再查身份
curl.exe -i http://localhost:8080/api/auth/me -H "Cookie: session_id=<粘贴sid>"

# 不依赖登录、随时可用的探针
curl.exe http://localhost:8080/api/system/info
curl.exe http://localhost:8080/api/system/health
```

> `system/info` 会返回实例名、Session 后端类型、Redis 是否连通、读写库角色 —— 排障时先看它。

## 6.8 两种运行模式对照

| | 单机最小版 | 完整集群版 | 本地开发模式 |
| --- | --- | --- | --- |
| compose 文件 | `simple.yml` | `docker-compose.yml` | 不用 compose |
| 后端副本 | 1 | 3 | 1（`--reload`） |
| MySQL | 单库 | 主从 + 读写分离 | SQLite 或本机 MySQL |
| Redis | 1 | 1 | 本机/Docker 一个 |
| 前端 | 容器内构建 | 容器内构建 | Vite 热更新 5173 |
| 入口 | `localhost:8080` | `localhost:8080` | `localhost:5173` |
| 适合 | 第一次跑通 | 学集群 | 改代码、看 `/docs` |

## 6.9 小结

- 先跑 `simple.yml` 建立信心，再跑完整集群；
- `SESSION_BACKEND` 一个环境变量就能切换「错误示范 / 正确示范」，是本教程的核心实验开关；
- 验证顺序：**能登录 → 副本在变 → 登录不掉 → 计数累加 → 主从同步 → 停一台仍可用**；
- 出问题先看 `ps`、再看 `logs`、最后用 `/api/system/info` 探针。
