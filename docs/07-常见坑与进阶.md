# 07 · 常见坑与进阶路线：从「能跑」到「能上线」

> 这一章是把教学项目搬到真实生产前的检查清单，也是你接下来几个月的学习地图。

---

## 7.1 集群环境下最容易踩的 8 个坑

### ① 文件上传存本地磁盘

```
上传到 backend-1 → 文件在 backend-1 的 /uploads
下载被派到 backend-2 → 404
```

**解法**：对象存储（S3 / OSS / MinIO）或共享文件系统（NFS）。应用只存 URL，不存文件本体。
**临时过渡**：Nginx `ip_hash` 把同一用户固定到一台 —— 但发布/扩容时会失效，别当长期方案。

### ② 定时任务每个副本都跑一遍

3 个后端各有一个 APScheduler，凌晨 2 点同一封日报发 3 次。

**解法**：
- Redis 分布式锁 `SET job:daily:lock <id> NX EX 300`（本项目 `init:schema:lock` 就是这个套路）；
- 或者干脆把定时任务拆成**独立服务 / K8s CronJob**，只跑一份（更推荐）。

### ③ WebSocket / SSE 长连接

连接是绑在某台后端上的，A 用户在 `backend-1`，B 用户在 `backend-2`，两人聊天消息互不可见。

**解法**：跨机广播用 Redis Pub/Sub（或专门的 IM 网关）；或者在 LB 层做基于 Cookie 的会话亲和。

### ④ 本地缓存导致数据不一致

`functools.lru_cache` 只在本进程生效，改了数据库，A 副本刷新了、B 副本还是旧的。

**解法**：共享缓存放 Redis；明确缓存失效策略（改数据时删 key，而不是等过期）；接受短暂不一致并写进文档。

### ⑤ 缓存与数据库的一致性

经典顺序问题：先删缓存再写库？先写库再删缓存？并发下都可能留下脏数据。

**常用方案**：**Cache-Aside + 延迟双删**，或者更彻底的 **CDC 订阅 binlog 异步失效缓存**（Canal / Debezium）。
Session 场景没这个问题，因为 Session 本身就是权威数据，不是数据库的副本。

### ⑥ 连接池被副本数放大

`3 个副本 × pool_size=20 = 60 个连接`，再加主从各一份 → 很容易打满 MySQL `max_connections=151`。
**解法**：算总量、调小每副本池、上 ProxySQL 做连接复用。这是扩容时最常炸的地方。

### ⑦ 日志与链路追踪

3 台机器各打各的日志，一个报错不知道是哪台。
**解法**：日志全输出到 stdout → 采集到 Loki / ELK；入口生成 `X-Request-ID` 并透传全链路；接 OpenTelemetry 做分布式追踪。

### ⑧ 滚动发布期间新旧版本并存

**解法**：接口向后兼容（先加字段、后删字段）；数据库迁移分三步走（加兼容结构 → 发应用 → 清旧结构）；发布前先扩一台新版本观察。

## 7.2 安全清单

| 项 | 教学版 | 生产必须 |
| --- | --- | --- |
| 传输加密 | HTTP | **HTTPS**（TLS 终止在 LB），Cookie 加 `Secure`，HSTS |
| 密码 | PBKDF2 + 盐 | 继续用 bcrypt/argon2；强制强度策略；登录失败限流 |
| XSS | Vue 默认转义 | 仍要防 `v-html`；加 CSP |
| CSRF | `SameSite=Lax` | 敏感操作加 CSRF Token / 二次确认；跨域场景用 `SameSite=None; Secure` 时必须配 token |
| SQL 注入 | SQLAlchemy ORM 参数化 | 永不拼 SQL 字符串 |
| Session | 随机 sid + HttpOnly | 登录成功后轮换 sid（已做）；异地登录提醒；绝对过期时间 |
| 越权 | 按 `user_id` 过滤 | 每个接口都校验「这条数据属不属于当前用户」，别只靠前端隐藏按钮 |
| 密钥 | 写在 compose 里 | 放 Secret Manager / 环境变量注入，**绝不进 Git** |
| Redis / MySQL | 教学密码 | 不暴露公网、改强密码、开防火墙白名单 |
| 限流 | 无 | Nginx `limit_req` / 网关限流，防刷登录接口 |

> 本项目 `GET /api/notes` 只返回当前用户的留言（`WHERE user_id = 当前会话用户`），
> 而不是「返回全部再让前端过滤」—— 这是最容易忽视的越权漏洞。

## 7.3 上生产还要补的组件

```
                      [ CDN / WAF ]
                           │
                    [ 云负载均衡 (多可用区) ]
                           │
                 ┌─────────┴─────────┐
            [ Nginx ×2 + Keepalived ]   ← 消除 LB 单点
                           │
              [ K8s Deployment / 弹性伸缩组 ]
                 backend 副本 × N（HPA 按 CPU/QPS 自动扩缩）
                           │
        ┌──────────────────┼──────────────────┐
   [ Redis 哨兵/集群 ]  [ MySQL 高可用 ]   [ 对象存储 ]
                           │
              [ 监控 Prometheus+Grafana / 日志 Loki / 告警 ]
                           │
              [ CI/CD: 测试→构建镜像→滚动发布→回滚 ]
```

**优先级建议**（别一次全上）：

1. **HTTPS + 备份**（数据安全底线）
2. **监控告警 + 集中日志**（否则出问题你不知道）
3. **CI/CD 自动化发布**（否则每次上线都靠手工，迟早出事）
4. **Redis 哨兵 / MySQL 高可用**（消除数据层单点）
5. **多 Nginx / 云 LB**（消除接入层单点）
6. **容器编排 K8s / 服务网格**（副本多了之后才需要）

## 7.4 术语速查（看文档不再卡壳）

| 术语 | 一句话 |
| --- | --- |
| 反向代理 | 替服务器接客，客户端不知道后端是谁 |
| upstream | Nginx 里「一组后端服务器」 |
| 水平扩容 / 垂直扩容 | 加机器 / 加配置 |
| 无状态 | 副本不存自己的用户数据 |
| 高可用 (HA) | 挂一台不影响服务 |
| 单点故障 (SPOF) | 挂了就全挂的那一环 |
| 滚动发布 / 蓝绿 / 金丝雀 | 逐步替换 / 两套切换 / 先放少量流量试水 |
| 最终一致 | 主从同步有延迟，过一会儿就一致 |
| 幂等 | 同一请求重复执行结果不变（重试的前提） |
| 熔断 / 降级 / 限流 | 下游坏了先别拖死自己 / 关掉非核心功能 / 限制请求速率 |
| 服务发现 | 副本 IP 老变，靠名字自动找到它们（Docker DNS / K8s Service / Consul） |
| 读写分离 / 分库分表 | 读流量分摊 / 把一张大表拆到多个库 |
| GTID / binlog | 全局事务编号 / MySQL 的变更日志 |
| TTL / LRU | 过期时间 / 最近最少使用淘汰 |
| 粘性会话 | 把同一用户固定派给同一台（临时方案） |

## 7.5 接下来学什么（路线图）

**基础巩固**
- HTTP 深入：状态码、缓存头（`Cache-Control`/`ETag`）、HTTPS/TLS 握手
- SQL：索引、执行计划 `EXPLAIN`、事务隔离级别
- Linux：进程、端口、systemd、日志

**后端进阶**
- FastAPI：依赖注入、Pydantic 校验、异步、后台任务
- Alembic 数据库迁移；SQLAlchemy 会话与事务边界
- 单元测试 / 集成测试（pytest + TestClient）
- 接口设计规范：REST、统一错误结构、分页、幂等键

**前端进阶**
- Pinia 持久化、路由守卫、Token 刷新、请求取消与竞态
- 打包优化、CDN、懒加载

**架构进阶**
- Docker 网络与数据卷、多阶段构建优化
- Nginx：缓存、限流、Lua、HTTPS 配置
- Redis：哨兵/Cluster 实操、Pub/Sub、Stream、分布式锁正确写法（Redlock 争议）
- MySQL：MGR / 分库分表 / 备份恢复演练
- 消息队列（Kafka / RabbitMQ）：削峰、解耦、最终一致
- K8s：Deployment / Service / Ingress / ConfigMap / HPA
- 可观测性：Prometheus + Grafana + OpenTelemetry

**推荐练手项目**：给本教程的项目依次加上「HTTPS」「上传头像到 MinIO」「用 Redis 做留言缓存并解决一致性」「用 pytest 写接口测试」「部署到一台云服务器并用 GitHub Actions 自动发布」。每加一个，都会回头用到这一章的某个知识点。

## 7.6 最后复述一遍整套逻辑

```
前后端分离  →  前端静态化、后端纯 API
      ↓
后端无状态  →  不本地存 Session / 文件 / 计数（否则无法扩容）
      ↓
水平扩容    →  Nginx 把请求轮询分给 N 个相同副本
      ↓
状态去哪儿  →  Redis 集中式 Session（号码牌在 Cookie，档案在 Redis）
      ↓
数据层扛住  →  MySQL 主从：写主库、读从库、binlog/GTID 同步、故障降级
      ↓
生产化      →  HTTPS + 高可用 + 监控 + CI/CD + 对象存储 + 追踪
```

**如果只记一句话**：
> 让用户状态**不落在任何一台会挂、会被替换的机器上**，你就拿到了随便加减机器的自由。

这句话能推导出本教程 80% 的设计决策。祝学习顺利，记得动手把实验 1 的 bug 亲手复现一次 —— 那一瞬间的「啊原来如此」，比读十篇架构文章都管用。
